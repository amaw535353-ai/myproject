# P11-A threat model — workload and Kubernetes platform isolation

P11-A moves the professional-mastery program from inference-runtime controls into the operating platform that runs AI workloads. The protected assets are tenant identity, service-account authority, model-serving container privileges, projected secrets and workload tokens, network reachability, namespaced RBAC, image integrity metadata, and host/runtime isolation boundaries.

The attacker can alter workload identity evidence, attempt to run as root or privileged, enable privilege escalation, add Linux capabilities, expose host namespaces or sockets, mount host paths, broaden writable filesystem paths, weaken seccomp/AppArmor, relax secret permissions, substitute secret sources, enable cloud-metadata or Kubernetes-API access, broaden RBAC, use mutable or untrusted images, remove image trust evidence, downgrade cgroup/user-namespace/LSM settings, or drop prior mastery debt. The matched vulnerable implementation trusts only the caller's final safety boolean.

The hardened path consumes the exact clean P10-I assessment and requires its incident-response and Phase 10 exit-gate positives while rejecting any P10-I production/nonclaim flag. It then binds the serving route to one tenant workload identity and requires a non-root UID/GID, bounded projected workload token, disabled default service-account-token automount, exact container/image coverage, no privileged or host-namespace surface, no added capabilities, `ALL` capability drop, RuntimeDefault seccomp, runtime/default AppArmor evidence, read-only root filesystems, allowlisted writable paths, read-only least-permission secret projections, default-deny network-policy evidence, no metadata or direct kube-API access, namespaced least-privilege RBAC, digest-pinned image trust evidence, cgroup-v2/user-namespace/LSM/device restrictions, and explicit carry-forward of unresolved mastery debt.

SHA-256 fields are integrity bindings, not cryptographic authenticity by themselves. `admission_verified` is deterministic evidence in this milestone; it does not prove that a production admission controller executed. Likewise network-policy evidence does not prove CNI enforcement, runtime-boundary evidence does not prove kernel containment or container-escape resistance, and workload-identity subject/audience evidence does not prove a cloud provider accepted the identity.

The executable Linux lab validates real local UID separation, `no_new_privs`, empty effective/bounding capabilities, secret file DAC, scoped write access, raw-socket denial, setuid-root denial, cross-tenant signal denial, cross-tenant `/proc/<pid>/environ` denial, Unix-socket DAC isolation, and user-namespace availability. It does **not** validate a live Kubernetes cluster, Kubernetes admission webhooks, CNI enforcement, production container runtime behavior, kernel escape resistance, cloud workload identity, or GPU/MIG/CUDA isolation.
